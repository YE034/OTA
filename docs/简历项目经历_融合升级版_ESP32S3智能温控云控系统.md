## 一、技术升级对照（先理解"为什么这么换"，面试必问）

| 维度 | 旧方案（STM32 温控风扇） | 升级后方案（本项目） | 升级理由（面试话术） |
|---|---|---|---|
| 主控/联网 | STM32F103C8T6 + ESP8266，双 MCU，USART2 走 AT 指令 | ESP32-S3 单核承载业务与协议栈，原生 Wi-Fi + BLE 5.0 | AT 指令是阻塞式请求-应答，串口带宽与实时性差、异常状态多；单芯片化降成本、去串口瓶颈，BLE 顺带解决配网问题 |
| 温湿度采集 | DHT11，单总线，精度 ±2℃ | SHT30（I²C，±0.3℃）+ NTC 经 ADC 采样做出风口温度冗余 | 高精度数字传感器 + 模拟采样链路（ADC/滤波）同时体现总线与模拟功底 |
| 人体检测 | HC-SR501 热释电 PIR，只能测"动" | 24G 毫米波雷达 HLK-LD241（UART），静态存在感应+距离 | PIR 检测不到静止人体；毫米波可判"人在/人离"，支撑无人节能策略 |
| 电机控制 | TB6612 开环 PWM 调速 | TB6612 + 霍尔测速，**增量式 PID 转速闭环**，含堵转保护 | 开环转速随电压/阻力漂移；闭环可量化稳态误差，且正好用上简历技能里的 PID |
| 摇头机构 | ULN2003 + 28BYJ-48，四拍通电 | 八拍细分时序 + 加减速曲线、角度软限位 | 细分驱动更平稳、降噪，体现步进电机时序控制深度 |
| 人机输入 | 4×4/独立机械按键、GPIO 扫描 | ESP32-S3 电容触摸通道（Touch）+ 中断消抖，保留按键冗余 | 用芯片特色外设替代机械扫描，支持触摸唤醒 |
| 状态指示 | 有源蜂鸣器 | WS2812（RMT 纳秒时序）做全彩状态灯 + LEDC 驱动无源蜂鸣器多音提示 | 状态语义更丰富，复用已掌握的 RMT 驱动 |
| 架构 | 主循环 + TIM2 定时中断 | FreeRTOS 5 任务 + 队列/事件组/互斥量，双核分工 | 业务与通信解耦，I²C 共享总线互斥保护，符合真实物联网终端架构 |
| 云端通信 | MQTT 明文，AT 透传，JSON 手工拼接 | MQTT **over TLS（8883，mbedtls）**，物模型 property/post·set·set_reply，QoS1 + LWT 遗嘱，cJSON 解析 | 与你实习的 AWS IoT 8883/TLS 方向完全对齐；LWT 保证离线状态可信 |
| 鉴权 | 简单设备 ID | ProductID/DeviceName 三元组 + HMAC-SHA1 动态签名 Token | 体现密码学签名与鉴权流程理解 |
| 参数存储 | 片内 Flash 模拟 EEPROM | NVS 键值存储（Wi-Fi 凭据、用户参数、OTA 断点） | 磨损均衡、掉电安全，接口标准化 |
| 数据可靠性 | 无 | LittleFS 离线数据缓存，断网补传；OTA 断点续传 | 弱网环境工程化思维，区分度高的亮点【可补做】 |
| 升级能力 | 无（只能有线烧录） | A/B 双分区 OTA：HTTPS 分块下载 + 流式 SHA-256 校验 + otadata 切换 + mark-valid 防回滚 | 原项目核心亮点保留，MD5 升级为 SHA-256，新增断点续传 |
| 配网 | 代码写死 SSID | BLE BluFi 配网 / SmartConfig，凭据写入 NVS【可补做】 | 量产设备不可能烧死 Wi-Fi，配网是完整产品闭环 |
| 低功耗 | 无 | 无人时 light-sleep / deep-sleep，雷达与定时器唤醒【可补做】 | 电池/节能场景加分项 |

## 二、推荐版（内容充实，作为简历主打项目，放项目经历第一条）

### 基于 ESP32-S3 与 OneNET 的多传感器智能温控云控系统（PID 闭环调速 / MQTT-TLS 云控 / A/B OTA）
**个人项目 · 独立开发** ｜ 2026.07 - 2026.08
**硬件平台**：ESP32-S3（双核 Xtensa LX7 @240MHz，16MB Flash，8MB PSRAM）
**技术栈**：C、ESP-IDF v4.4.3、FreeRTOS（任务/队列/事件组/互斥量/看门狗）、MQTT over TLS（mbedtls/8883）、HTTP/HTTPS Client、cJSON、I²C、ADC、RMT、LEDC、Touch、NVS、LittleFS、A/B 双分区 OTA、HMAC-SHA1、中国移动 OneNET 物模型、CMake

**项目描述**：
系统以 ESP32-S3 为核心，融合温湿度/光照/毫米波人体存在多传感器感知、直流风扇 PID 闭环调速、步进电机摇头、OLED 菜单与触摸交互，通过 MQTT-TLS 接入中国移动 OneNET 云平台，实现环境数据加密上行、远程/本地双端实时控制、设备影子状态同步与 A/B 双分区 OTA 远程升级；采用 BSP 驱动层—RTOS 系统层—业务应用层—云协议层四层解耦架构，具备断线重连、离线缓存补传、异常自愈与防回滚升级能力。该项目由早期 STM32F103+ESP8266(AT) 双芯片版本重构升级而来，单芯片化后消除了 AT 串口瓶颈并补齐了安全通信与远程运维能力。

**主要工作**：
- **四层分层架构与 FreeRTOS 多任务设计**：基于 ESP-IDF 组件机制拆分为传感器采集、控制决策、人机交互（OLED/触摸/RGB）、云通信、OTA 共 5 个低耦合组件；运行期划分 5 个 FreeRTOS 任务——采集任务（200ms 周期）经互斥量保护共享 I²C 总线轮询 SHT30/BH1750，ADC+DMA 采样 NTC 并做一阶低通+滑动均值滤波；控制任务（100ms）运行状态机与 PID；通信任务绑核 CPU0 处理 Wi-Fi/协议栈，业务任务运行于 CPU1；任务间以 Queue 传递传感器结构体、EventGroup 同步联网状态，用 `uxTaskGetStackHighWaterMark` 排查并收敛各任务栈占用。
- **PID 闭环调速与执行机构驱动**：TB6612 驱动直流风扇，霍尔脉冲经 GPIO 中断计数实测转速，内环采用**增量式 PID**（积分限幅、输出限幅、抗积分饱和）闭环跟踪目标转速，稳态误差 <3%；外环在自动模式下按"目标温度—环境温度"差值经带死区分段策略映射目标转速，避免临界温度附近频繁启停；实现堵转保护（连续多个控制周期实测转速为 0 即停 PWM 并上报告警）；ULN2003 步进摇头采用八拍细分时序并加梯形加减速曲线与角度软限位；WS2812 状态灯经 **RMT 外设**按纳秒级单总线时序编码 GRB（80MHz 八分频，1 tick=100ns），以颜色语义区分待机/自动/告警/配网状态。
- **毫米波存在感应与低功耗节能策略**：UART1 对接 24G 毫米波雷达（移植环形缓冲区 RingBuffer + 串口接收中断实现异步帧缓存、主循环按协议解析，解决高速串口丢包），输出人体存在/运动距离；状态机据此联动——人在自动调速、人离 5 分钟降速息屏、长时无人进入 light-sleep 并由雷达 GPIO 唤醒，平均工作电流显著下降【功耗数值建议实测后补】。
- **MQTT-TLS 安全通信与 OneNET 物模型全双工对接（核心）**：基于 esp_event 默认事件循环 + 事件组实现 STA 联网状态同步与断线自动重连、重订阅；内置 OneNET CA 根证书，经 **mbedtls 走 8883 端口建立 TLS1.2 加密通道**，使用设备三元组按 HMAC-SHA1 动态签名生成限时 Token 完成鉴权；按物模型实现属性上报（温湿度/光照/转速/模式/存在状态/固件版本，3s 周期，QoS1）、属性设置下行（property/set）与 set_reply 应答，cJSON 统一解析 number/bool/string 三类参数并分发至控制层，支持远程开关、调档、模式切换、摇头、RGB 变色与定时；配置 **LWT 遗嘱消息**保证设备异常掉线时云端状态可信；用 topic_len+memcmp 精确匹配非 `\0` 结尾主题，端到端控制延迟 <1s。
- **弱网可靠性设计**：Wi-Fi 凭据与用户参数存 NVS（替代旧方案片内 Flash 模拟 EEPROM，掉电不丢、磨损均衡）；上报失败的数据按行写入 **LittleFS 本地环形日志**，MQTT 重连成功后按时间序补传并清理，实现断网不丢数据【可补做】；联网后经 SNTP 对时，支持 RTC 定时开关机计划；首启无凭据时经 **BLE BluFi** 手机配网并写入 NVS【可补做】。
- **A/B 双分区 OTA 远程升级（核心）**：自定义 16MB 分区表（ota_0/ota_1 双 APP 分区 + NVS/otadata/LittleFS），独立 OTA 任务实现「MQTT 升级通知 → HTTPS 版本与任务校验 → 分块下载写入备用分区 → 流式 SHA-256 完整性校验 → 切换 otadata 启动指针 → 重启 mark-valid」完整链路；升级期间挂起周期上报任务规避网络/内存竞争，重启前经回调优雅释放 MQTT/Wi-Fi（以回调注入方式避免组件循环依赖）；实现防重入、失败重试、Content-Length 校验、NVS 记录 offset + HTTP Range **断点续传**【可补做】、新固件未确认即回滚的防回滚机制，升级失败自动回退原固件、零变砖；实测约 860KB 固件 19s 内完成下载与切换。
- **底层稳定性攻关**：定位并关闭 modem-sleep，规避片内温度/ADC 采样与 PHY/RTC 时钟冲突导致的任务看门狗（TWDT）复位；实现 I²C 总线挂死的 SCL 手动时钟恢复；TLS 握手内存峰值超预算时裁剪 mbedtls 证书链与会话缓冲并将大缓冲区迁至 PSRAM；统一注册 TWDT 喂狗点与 `esp_reset_reason()` 复位原因统计，异常重启后自愈恢复。

**项目成果**：
设备经 TLS 稳定接入 OneNET，多传感器上报与远程/本地双端控制端到端延迟 <1s，转速闭环稳态误差 <3%；连续多版本 OTA 均一次成功、失败可回滚零变砖；离线缓存补传与断线重连机制保障弱网下数据零丢失。系统掌握了 FreeRTOS 多任务并发与同步、ESP-IDF 外设驱动、PID 闭环控制、MQTT 物模型与 TLS 安全通信、嵌入式 OTA 全流程设计，与实习中 EC200U + MQTT/TLS(8883) 接入云平台的工作形成技术印证。

## 五、面试高频考点（对照准备，确保每条都能讲清）

### A. 架构与 RTOS
1. **为什么从 STM32+ESP8266 换成 ESP32-S3？**（必问题，讲演进）
   AT 指令方案是主控经串口发 AT、等 OK/ERROR 的阻塞模型，联网状态机脆弱、串口是吞吐瓶颈（之前靠 RingBuffer 补救丢包）、双 MCU 成本高且无法做安全 OTA；ESP32-S3 把 Wi-Fi/BLE/TCP-IP 协议栈与业务集成在一颗芯片上，腾出的 MCU 资源用来做 TLS、PID 和文件系统。
2. **五个任务怎么划分？为什么这么划？**
   按"周期不同、阻塞源不同"划分：采集 200ms（I²C 阻塞）、控制 100ms（实时性最高）、UI 200ms、通信事件驱动（网络阻塞最久，必须独立）、OTA 平时阻塞等信号量。通信绑 CPU0（Wi-Fi 协议栈默认在 CPU0，减少核间开销），控制在 CPU1 保证实时性。
3. **共享 I²C 总线上挂了 SHT30、BH1750、OLED，怎么防冲突？**
   互斥量包裹"I²C 起始→传输→释放"完整事务；并实现 SCL 手动发 9 个时钟的总线挂死恢复，防止某从机拉住 SDA。
4. **事件组怎么同步"拿到 IP 再启 MQTT"？** Wi-Fi GOT_IP 回调置位，通信任务 xEventGroupWaitBits 阻塞等待，断线清位重连、重订阅。

### B. 控制算法与外设
5. **增量式 PID 公式？为什么用增量式不用位置式？**
   Δu=Kp(e-e1)+Ki·e+Kd(e-2e1+e2)，增量式只与近三次偏差有关、输出为增量，切换手动/自动时无冲击，且自带积分截断方便限幅；补充积分限幅与抗饱和（积分到输出饱和边界即停止累加）。
6. **外环温度、内环转速为什么串级？** 温度是大惯性慢变量、转速是快变量，分环后内环快速抑制电压波动/风阻扰动，外环只负责按温差给目标转速；死区防止温度在目标值附近抖动导致频繁变速。
7. **堵转怎么判？误报怎么办？** 输出占空比 >阈值但连续 N 拍霍尔计数为 0 才判堵转，N 拍是去抖；停机→RGB 红光+蜂鸣器→云端告警三件事联动。
8. **RMT 为什么能驱动 WS2812？为什么发 GRB？**
   WS2812 用纳秒级高低电平脉宽编码 0/1，bit-bang 会被中断打断，RMT 是硬件专用发送通道，按 tick 精确出波形；灯珠内部三通道物理顺序是 GRB，故内存中调换 R/G 字节。
9. **ADC 采样链路？** NTC 分压→ADC 连续采样+DMA 搬运→一阶低通（α 滤波）+滑动均值，抑制工频与风扇电机 PWM 干扰，再查 B 值公式表换算温度。

### C. 通信、安全与云平台
10. **MQTT over TLS 握手过程？8883 和 1883 区别？**（与你实习强相关，重点准备）
    TCP 三次握手后 TLS1.2 握手：ClientHello→证书链验证（内置 OneNET CA，mbedtls 校验）→密钥协商→对称加密会话；1883 明文、8883 走 TLS。讲清你怎么解决 TLS 内存峰值（裁剪证书校验链、缓冲区放 PSRAM）。
11. **OneNET 鉴权 Token 怎么生成？** ProductID/DeviceName/设备密钥做 HMAC-SHA1，对拼接签名串签名后 base64，设置 exp 过期时间；对比你实习接触的 AWS IoT（证书/双向认证）差异，是加分谈资。
12. **QoS1 流程？LWT 解决什么问题？** PUBLISH→PUBACK 保证至少一次，因此下行执行要幂等；LWT 是连接时预先登记遗嘱，设备异常掉线 Broker 代为发布"离线"，解决设备死了自己来不及上报的问题。
13. **物模型 topic 有哪些？set_reply 为什么必须回？** post 上报、set 下行、set_reply 应答；平台等应答做指令超时判定，不回会在控制台显示执行失败。主题非 `\0` 结尾，用长度+memcmp 匹配而非 strcmp。
14. **cJSON 解析注意什么？** 判空链（obj→成员→类型），解析完 cJSON_Delete 防内存泄漏；number/bool/string 分派到统一执行函数。

### D. OTA（你的核心亮点，往深里准备）
15. **为什么 A/B 双分区？完整流程？** 运行 ota_0 时新固件写 ota_1，写坏/断电仍从 ota_0 启动；流程：MQTT 通知→HTTPS 下载→esp_ota_write 分块写备用分区→SHA-256 流式校验→set_boot_partition 改 otadata→重启→新固件自检 mark_app_valid，否则回滚。
16. **otadata / PENDING_VERIFY / mark valid？** otadata 存启动分区指针；新固件首次启动是待验证态，业务自检通过才 mark valid，否则下次启动 bootloader 自动回滚旧分区。
17. **为什么边下载边算 SHA-256（流式校验）？** 860KB 固件不必整块驻留内存，每分片 update、最后 final 比对；SHA-256 替代 MD5 是抗碰撞强度考虑。
18. **断点续传怎么做？** 下载前把已写 offset 存 NVS，中断后用 HTTP Range: bytes=offset- 向服务器续传，esp_ota 继续追加；下载完成清掉该键。【可补做】
19. **OTA 时为什么挂起上报任务？** 下载占带宽与堆内存，并发 MQTT 收发会造成内存竞争甚至分配失败；预重启回调由 main 注入（OTA 组件不直接依赖 MQTT 组件，避免循环依赖）。

### E. 可靠性与低功耗
20. **离线补传怎么设计？** LittleFS 追加写 CSV 行（时间戳+各属性），环形覆盖最旧数据；重连后逐帧补发、收到平台侧成功再删行，保证 at-least-once。
21. **TWDT 怎么定位的？** 现象是周期性复位、日志停在温度读取处；根因是 modem-sleep 时钟源与传感器读取冲突使任务自旋、IDLE 得不到喂狗；关闭 modem-sleep + 读取前后喂狗 + vTaskDelay 让出。
22. **light-sleep 和 deep-sleep 区别？唤醒源？** light-sleep 保 RAM、CPU 暂停、毫秒级唤醒；deep-sleep 只保 RTC 内存，用雷达 GPIO  ext0/ext1 或定时器唤醒，恢复后按复位流程重跑、靠 NVS 恢复状态。
